# Interface Hub UI 재설계

이 문서는 디자인 검토용이다. 제품 React, API, DB는 바꾸지 않았다. 화면 시안은 `design/ui-redesign/index.html`이며 API를 호출하지 않는다.

2차 시안이 현재 제안이다. 1차의 프로젝트 목차, 개요, Endpoint 목록, Method/Path, 탭, 인라인 필드, 상단 저장, 이력·Markdown 위치는 유지한다. 베이지 배경, 명조 제목, 검은 상단 바, 항상 열린 입력 칸은 제외한다. 2차는 흰색·뉴트럴 그레이, 차콜 사이드바, 블루 강조, Pretendard와 모노스페이스다. 기준 폭은 1440px이고 1280px까지 지원한다. 모바일 레이아웃은 두지 않는다. JSON 예시는 기본으로 닫혀 있고, 필드 값은 행을 선택하기 전까지 글자로 읽힌다.

1차에서 정리한 제품 UI 문제는 아래에 그대로 둔다.

샘플 프로젝트 이름은 기존 Markdown 예시의 "포장 라인"이다. 운영 데이터와 무관하다.

## 1. 현재 UI에서 본 문제

검토한 화면은 프로젝트 목록, 프로젝트 상세, REST API, MQTT, WebSocket, 장비 프로토콜, 일반 문서, 오류 코드, 변경 이력, Markdown이다. 공통 골격은 남색 사이드바, 흰 카드, 8px 모서리, 파란 주요 버튼이다.

### 처음 들어왔을 때 할 일이 보이지 않는다

현재: 프로젝트 목록은 이름, 상태, 생성자, 날짜, 권한 표다. 상세는 프로토콜 카드 여섯 장과 멤버 탭이다. 마지막에 무엇을 고쳤는지는 없다.

불편: 개발자는 "어디를 이어서 쓸지"를 카드 설명 문장에서 추론해야 한다.

방향: 프로젝트 안을 작업 공간으로 두고, 최근 변경과 이어 쓸 항목을 위쪽에 둔다.

### Endpoint 하나를 만들기까지 단계가 길다

현재: 문서가 없으면 상세의 "API 규격 작성 시작" 다음 편집기의 "API 규격 시작"이 한 번 더 있다. 문서가 있으면 편집기로 들어간 뒤 "+ Endpoint 추가"를 누른다. 추가 직후 Method, Path, 이름, 요약, 설명, Request 트리, Response 카드, 오류 코드 목록이 한 스크롤에 펼쳐진다. 저장과 변경 사유는 맨 아래다.

불편: 첫 필드를 쓰기 전에 비어 있는 입력 구역을 지나가야 한다. 저장 버튼은 스크롤 끝에 있다.

방향: 새 Endpoint는 Method, Path, 이름만 먼저 받는다. 요청, 응답, 파라미터, 오류 코드는 탭으로 나눈다. 변경 사유와 저장은 문서 제목 옆에 고정한다.

### 입력란이 필요 전부터 펼쳐져 있다

현재: 필드 하나마다 카드가 열린다. 필드명, 타입, 필수, Nullable, 설명, 예시, Format, 순서 버튼, 삭제 버튼이 항상 보인다. 객체는 하위 필드 영역까지 펼친다. Response도 이름, 상태 코드, 설명, 예시 모드, 빈 트리를 카드로 연다.

불편: 필드 세 개가 화면의 대부분을 차지한다. Nullable과 Format은 자주 비어 있다.

방향: 기본 편집은 표의 한 줄이다. 열은 필드, 타입, 필수, 설명, 예시다. Nullable, Format, Enum, 순서, 삭제는 행을 선택했을 때 연다. 중첩은 들여쓰기로 보여 주고 데이터 모델은 지금과 같다.

### 같은 정보가 반복된다

현재: 셸 제목, 페이지 제목, 문서 버전 알약, 오른쪽 JSON 패널의 "기준 버전"이 버전을 각각 말한다. 조회 모드의 표와 편집 모드의 카드가 같은 필드를 다른 형태로 그린다. 상세 카드의 문장과 편집기 빈 상태가 다음 행동을 두 번 설명한다.

불편: 시선이 상태 표시를 찾고, 내용은 아래에 남는다.

방향: 버전은 문서 경로에 한 번만 둔다. 조회와 편집은 같은 표 구조를 쓰고, 편집일 때만 칸이 입력이 된다.

### 가로 공간을 카드 테두리가 먹는다

현재: 편집기는 270px 목록, 본문, 320px JSON의 세 칸이고 각 칸이 흰 카드다. JSON은 Endpoint를 열자마자 고정 폭을 차지한다. 프로젝트 상세의 카드는 같은 높이로 프로토콜을 나열한다.

불편: 본문 열이 줄고, 아직 필드가 없어도 JSON 패널은 자리를 유지한다.

방향: JSON 예시는 1440px과 1280px 모두 기본으로 닫는다. 열면 오른쪽 분할이 되고, 닫으면 편집 영역이 다시 넓어진다. 프로젝트 현황은 같은 높이의 카드 대신 한 줄 목록으로 둔다.

### 조회와 편집의 전환이 어색하다

현재: "편집"과 "조회로 전환"이 화면 전체를 바꾼다. 조회는 읽기 표, 편집은 다른 구조의 폼이다. 편집에 들어가면 문서 상단, 인증, 오류 코드까지 같이 열린다.

불편: 설명 한 줄을 고치려고 전체 작성 폼으로 들어간다.

방향: 같은 문서에서 읽기/편집만 바꾼다. 저장 막대만 편집에서 나타난다.

### 프로토콜 작업 방식이 비슷하면서도 각각 따로다

현재: REST, MQTT, WebSocket, 장비 페이지가 같은 3단 골격과 다른 본문 순서를 가진다. 빈 상태에서 누르는 버튼 문구도 페이지마다 두 단계다.

불편: 프로토콜을 옮겨 갈 때 저장 위치와 목록 위치를 다시 찾는다.

방향: 목차, 문서 제목, 저장 막대, 탭, 이력, Markdown의 위치를 같게 한다. 탭 내용만 프로토콜 데이터에 맞춘다.

### 개발 작업 공간처럼 보이지 않는다

현재: 사이드바 항목은 프로젝트, 내 정보, 계정 관리뿐이다. 프로젝트 안의 규격은 본문에 들어간 뒤에야 보인다.

불편: 규격 사이를 이동하려면 상세로 나갔다가 다른 카드를 연다.

방향: 프로젝트에 들어가면 왼쪽이 그 프로젝트의 목차가 된다. 개요, 네 규격, 오류 코드, 일반 문서, 설정이 한 탐색에 있다.

### 이력과 Markdown이 본문과 같은 급의 탭이라 작업 중에 숨는다

현재: 규격, 변경 이력, Markdown이 본문을 통째로 교체한다. 기능은 있으나 작성 화면에서는 버전 알약만 보인다.

불편: 방금 저장한 차이가 무엇인지, 어떤 Markdown이 나가는지 보려면 작성 화면을 떠나야 한다.

방향: 이력과 Markdown은 문서의 동작으로 목차에 남긴다. 열어도 프로젝트 목차와 문서 경로는 유지한다. 기본 화면은 계속 규격 작성이다.

### 관리자 페이지처럼 보이는 이유

현재 인상은 기능이 부족해서가 아니다. 남색 사이드바, 균일한 카드, 회색 배경 위 흰 상자, 파란 버튼, 모든 라벨이 같은 굵기의 폼이 합쳐져 일반적인 관리 화면의 공식이 된다. 규격 문서를 읽는 느낌보다 설정을 입력하는 느낌에 가깝다.

방향: 카드 테두리를 줄이고, 제목은 Pretendard, 경로와 JSON은 고정폭, 강조색은 블루 하나로 둔다.

## 2. 컨셉 후보

세 안 모두 기존 데이터와 저장 규칙을 유지한다. 화면만 다르다.

### 규격지

프로젝트를 한 권의 규격으로 본다. 왼쪽은 목차, 가운데는 지금 보는 문서, 예시는 필요할 때 옆면이다. 필드 편집은 표의 행이다.

맞는 점: 공식 문서, 공유, 이력, Markdown이 한 문서의 동작이 된다. 작성 칸이 줄어 첫 Endpoint가 짧아진다.

약한 점: 필드의 부가 속성(Nullable, Format, Enum)은 한 단계 뒤에 있다. 발견되지 않게 행 선택에 붙여야 한다.

### 작업대

Postman에 가까운 항상 열린 3단이다. 목록, 요청 편집, 예시가 동시에 보이고 색은 더 어둡다.

맞는 점: 예시와 필드를 동시에 비교하기 좋다.

약한 점: 요청을 보내는 도구처럼 보인다. Interface Hub는 호출 실행기가 아니다. 빈 예시 열이 다시 넓이를 차지한다.

### 기록부

GitHub에 가깝게 프로젝트 첫 화면을 변경 목록과 파일 트리로 둔다. 편집기는 파일을 연 다음 나온다.

맞는 점: 이력과 검토가 잘 드러난다.

약한 점: 매일 하는 일이 이력 확인이 아니라 Endpoint 작성이다. 첫 화면이 쓰기보다 읽기에 기울면 작성 단계가 다시 길어진다.

## 4. 프로젝트 상세

1440px 구조:

1. 왼쪽 차콜 목차: 개요, 네 규격과 개수, 오류 코드, 일반 문서, 전체 이력, 설정. 별도의 상단 바는 없다.
2. 본문 위: 프로젝트명, 설명, 현재 상태
3. 이어서 작업과 최근 변경을 나란히 둔다
4. 규격·문서 한 줄 목록

한 줄에는 이름, 버전과 규모, 열기, 항목 추가가 있다. 카드 그리드는 쓰지 않는다. 멤버와 보관, 제목 수정은 목차의 프로젝트 설정으로 옮기되 권한 규칙은 유지한다.

1280px: 사이드바를 260px로 줄이고 본문은 남은 폭을 쓴다. 모바일 화면은 지원하지 않는다.

## 5. REST API 편집기

1440px 구조:

1. 왼쪽은 Endpoint 목록이다. 프로젝트 개요로 돌아가는 항목이 위에 있다.
2. 목록 위: 문서 정보(Base URL, 공통 인증, 공통 헤더)와 검색
3. 목록: Method와 Path. 아래: 변경 이력, Markdown
4. 본문 위: Method와 Path를 한 입력으로 두고, 그 아래 이름과 설명. 저장은 오른쪽 상단에 둔다. 변경 사유는 저장을 누를 때 입력한다.
5. 탭: 요청, 응답, Header·Path·Query, 오류 코드
6. JSON 예시는 기본으로 닫혀 있다. 열면 오른쪽 분할이고, 닫으면 편집 영역이 다시 넓어진다. 자동/직접 전환은 유지한다.

새 Endpoint는 목록의 "+ Endpoint 추가"가 Method, Path, 이름만 있는 짧은 입력을 연다. 만들기 전에는 서버에 저장하지 않는다. 저장을 눌러야 지금과 같이 문서 Version이 오른다.

응답이 여러 개면 탭 이름이 "응답 200"처럼 상태 코드를 보여 주고, 탭 안에서 응답을 추가한다. 기본 200 응답 데이터는 계속 만들어 둔다. 화면에서만 접는다.

1280px: 예시 패널을 열면 340px을 쓰고 필드 표는 남은 폭을 유지한다. 모바일 서랍은 두지 않는다.

## 6. Endpoint를 저장하기까지

문서가 이미 있을 때:

1. 프로젝트 개요에서 "Endpoint 추가" 또는 편집기 목록의 "+ Endpoint 추가"
2. Method, Path, 이름 입력 후 만들기
3. 요청 탭의 표에 필드를 행으로 추가
4. 필요하면 응답, 파라미터, 오류 코드 탭으로 이동
5. 제목 옆 변경 사유를 적고 저장

문서가 없을 때:

1. 개요의 REST API 행에서 문서를 한 번만 시작
2. 바로 Endpoint 입력으로 이어짐

지금처럼 "작성 시작"과 "규격 시작"을 두 화면에서 반복하지 않는다. 서버에는 지금과 같이 문서 생성 한 번, 항목 저장 한 번이다.

조회 권한과 보관 프로젝트는 추가와 저장을 보여 주지 않는다. 409가 나면 지금처럼 입력은 유지하고, 확인 뒤에만 그 항목을 다시 저장한다.

## 7. 전후 비교

| 상황 | 현재 | 규격지 |
| --- | --- | --- |
| 프로젝트에 들어온 직후 | 같은 크기의 기능 카드 | 최근 변경, 이어 쓰기, 규격 목록 |
| 다른 규격으로 이동 | 상세로 나간 뒤 카드 선택 | 왼쪽 목차 |
| 새 Endpoint의 첫 입력 | Method, Path, 이름, 요약, 설명, Request, Response가 한 페이지 | Method, Path, 이름 다음 요청 표 |
| 필드 하나 | 카드와 7개 안팎의 라벨 | 표의 한 행. 부가 속성은 행 선택 |
| 저장 | 스크롤 끝 | 경로 옆에 고정 |
| JSON | 항상 320px | 기본은 닫힘. 열면 우측 분할, 닫으면 편집 영역이 넓어짐 |
| 조회/편집 | 서로 다른 레이아웃 | 같은 표, 입력만 전환 |
| 이력, Markdown | 본문을 바꾸는 최상위 탭 | 문서 목차의 동작. 경로 유지 |

유지되는 데이터: Method, Path, 이름, 요약, 설명, 상태, 인증, 공통 헤더, Header, Path, Query, Request, Response 여러 개, 중첩 객체와 배열, 필수, Nullable, Format, Enum, 예시 자동/직접, 오류 코드 참조, 변경 사유, 순서, 문서 Version, 409, 권한, 보관.

## 8. 다른 화면에 적용할 공통 원칙

- 프로젝트 목차와 위 막대는 모든 규격, 일반 문서, 오류 코드가 같이 쓴다.
- 항목 목록은 왼쪽, 본문은 하나, 보조 보기(JSON, HEX, Markdown 미리보기)는 닫을 수 있는 옆면이다.
- 항목의 식별자만 제목 줄에 둔다. REST는 Method와 Path, MQTT는 Topic, WebSocket은 이벤트 이름, 장비는 Command ID다.
- 상세 속성은 탭이나 행 선택 뒤로 보낸다. 저장하지 못하는 필드를 만들지는 않는다.
- 변경 사유와 저장은 같은 위치다.
- 변경 이력과 Markdown은 같은 자리의 문서 동작이다.
- 빈 상태는 다음 입력 한 가지와 짧은 문장만 둔다. 관리 화면형 카드 설명을 반복하지 않는다.
- 강조색은 저장과 현재 위치만. Method와 방향은 작은 글자색으로만 구분한다.

프로토콜별 탭 내용만 다르다.

- MQTT: Payload, 발행·구독, 대응 Topic, 오류 코드
- WebSocket: Payload, 연결·종료 코드, 대응 메시지, 오류 코드
- 장비: 바이트 표, HEX, 대응 명령, 오류 코드. Offset과 Length 검증 문구는 표 옆에 유지한다.
- 일반 문서: 목록과 본문, 미리보기는 옆면
- 오류 코드: 목차 안의 표. 참조 위치는 해당 규격 항목으로 연결

## 9. 구현 시 수정 대상

이번 단계에서 수정하지 않는다. 승인 후 예상 범위다.

- `web/src/styles/tokens.css`, `shell.css`, `components.css`, `spec.css`

- `web/src/pages/SpecPage.tsx`

## 10. 작업 순서와 위험

1. 셸과 프로젝트 목차
2. 프로젝트 개요
3. REST 편집기의 표와 탭, 저장 막대
4. 조회 모드를 같은 표로 맞춤
5. 이력과 Markdown을 목차 동작으로 이동
6. MQTT, WebSocket, 장비, 일반 문서, 오류 코드에 같은 골격 적용

위험:

- 표로 바꾸면서 Nullable, Format, Enum, 배열 요소, 8단계 중첩, 장비의 Offset과 Encoding을 빼면 기존 저장 내용이 화면에서 사라진다. 구현 시 행 상세에 모두 남겨야 한다.
- 409와 임시 초안, 순서 변경, 검색 중 순서 잠금은 지금 동작 그대로여야 한다.
- 문서 상단 저장과 항목 저장은 다른 요청이다. 한 버튼으로 합치지 않는다.
- 오류 코드는 규격 화면에서 생성하지 않는 현재 규칙을 유지한다.
- 좁은 화면에서 필드 표를 다시 큰 카드로 되돌리면 이번 문제가 재발한다.

## 11. 승인받을 결정

1. 추천 컨셉을 규격지로 할지
2. 프로젝트 안의 남색 기능 사이드바를 목차로 바꿀지
3. 필드 카드를 표 행으로 바꿀지
4. 요청, 응답, 파라미터, 오류 코드를 탭으로 나눌지
5. JSON 예시를 1440px과 1280px 모두 기본 닫힘으로 둘지
6. 이력과 Markdown을 최상위 탭 대신 문서 목차의 동작으로 둘지
7. 새 Endpoint의 첫 입력을 Method, Path, 이름으로 줄일지. 요약, 설명, 기본 200 응답은 저장 전에 기본값으로 채운다.
