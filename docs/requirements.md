# Interface Hub - Requirements

## 1. 문서 상태

2차 검토에서 OQ-01부터 OQ-18까지 확정했다. 이 문서의 정책이 권한, 범위, 상태 규칙의 기준이다.

구현은 아직 시작하지 않는다. Backend, Frontend, DB Migration 파일 생성과 실행, 운영 서버 배포는 이번 단계에 포함되지 않는다.

기준 문서는 다음 한 가지 주제만 맡는다.

| 주제 | 기준 |
|---|---|
| 정책, 권한, 범위 | `docs/requirements.md` |
| 실행 구조, 잠금 절차, 메일 순서, 배포 분리 | `docs/architecture.md` |
| 테이블, JSON 형태, Migration 절차 | `docs/database.md` |
| 화면과 편집기 | `docs/ui-design.md` |
| HTTP | `docs/api.md` |

정책이 다른 문서와 다르면 이 문서를 따른다. 저장 형태가 다르면 `docs/database.md`를 따른다. 구현 중 정책을 임의로 바꾸지 않는다.

`docs/tasks.md`는 아직 확정하지 않는다.

---

## 2. 배경과 목표

연구소의 SW, APP, FW, GW, HW 부서가 하나의 프로젝트를 함께 개발한다. API, MQTT, WebSocket, 장비 프로토콜 규격이 부서별로 흩어져 최신 기준을 맞추기 어렵다. 프로젝트가 끝나면 부서별 기술 문서와 절차도 한곳에 남아 있어야 한다.

Interface Hub는 다음을 제공한다.

1. 규격 종류별 전용 편집기로 항목을 하나씩 작성한다.
2. 조회 화면에서 표, 필드 설명, 요청·응답·Payload, JSON 또는 HEX 예시로 읽게 한다.
3. 프로젝트의 규격 종류마다 공식 문서를 최대 1개만 둔다.
4. 누가 언제 무엇을 왜 바꿨는지 남기고, 항목의 추가·수정·삭제를 구분해 비교한다.
5. 부서별 기술 문서와 일반 산출물을 프로젝트 단위로 모은다.

Swagger, RapiDoc, Postman은 참고 사례다. 특정 제품 화면을 복제하지 않는다.

화면의 사용성에 맞춰 데이터 구조를 정한다. 사용자가 테이블 구조에 맞춰 JSON이나 Markdown을 직접 작성하게 하지 않는다.

## 3. 사용자

- 사용자는 연구소 내부 직원만이다.
- 회원가입은 없다.
- 로그인 ID는 사번이다.
- 기본 정보는 사번, 성명, 이메일이다. 이메일은 필수다.
- MASTER가 계정을 만들고 수정하고 비활성화한다.
- 규모는 약 50명이다.
- 비밀번호는 bcrypt 해시만 저장한다. 원문, 해시, 재설정 토큰은 응답과 로그에 넣지 않는다.
- MASTER의 비밀번호 초기화는 30분짜리 일회용 설정 링크다. 메일 본문에 비밀번호를 적지 않는다.
- 로그인한 사용자는 현재 비밀번호를 확인한 뒤 본인 비밀번호를 바꾼다.
- 사용자 일괄 등록, 일괄 초기화, 일괄 메일 발송은 1차 범위가 아니다.

계정 관리는 핵심 기능이 아니다. 1차는 로그인, MASTER의 개별 계정 생성·수정·비활성화, 개별 링크 초기화, 본인 비밀번호 변경만 둔다.

최초 MASTER는 CLI로만 만든다. 서버 기동 때 고정 계정을 만들지 않는다. MASTER는 여러 명일 수 있다.

Access Token은 8시간이다. Refresh Token은 없다. 만료되면 다시 로그인한다.

## 4. 역할과 프로젝트 권한

시스템 역할과 프로젝트 권한은 별도이다.

| 역할 | 의미 |
|---|---|
| MASTER | 계정 관리. 모든 프로젝트의 상세, 문서, 이력, 멤버 관리에 접근 |
| MEMBER | 로그인한 일반 사용자 |

| 프로젝트 권한 | 의미 |
|---|---|
| 없음 | 제목 목록의 공개 열만 볼 수 있다 |
| READ | 상세, 문서, 에러 코드, 이력, Markdown을 조회한다 |
| WRITE | READ를 포함한다. ACTIVE 프로젝트에서 규격 항목, 일반 문서, 에러 코드를 등록·수정하고, 항목·일반 문서·에러 코드를 삭제한다. 공식 규격 문서 자체는 삭제하지 않는다 |

권한은 문서별이 아니라 프로젝트별이다. 저장은 사용자당 READ 또는 WRITE 한 행이다.

- 로그인한 사용자는 프로젝트를 만들 수 있다.
- 생성자는 `created_by`로 남고 WRITE 한 행을 받는다.
- 로그인한 사용자는 전체 프로젝트의 제목, 상태, 생성자 이름, 생성일, 내 권한을 본다.
- 권한이 없는 프로젝트의 설명, 문서, 에러 코드, 이력은 내려주지 않는다.
- 상세 화면은 READ 이상과 MASTER만 연다.
- Frontend에서 버튼을 숨기는 것만으로 권한을 대신하지 않는다. Backend가 매 요청을 검증한다.
- MASTER가 문서를 고치면 이력의 수정자는 그 MASTER 계정이다.

### 4.1 권한을 바꿀 수 있는 사람

프로젝트 권한의 부여, 변경, 회수는 MASTER와 그 프로젝트 생성자만 한다.

WRITE 멤버는 문서를 다룰 수 있다. 다른 사용자의 프로젝트 권한은 바꿀 수 없다.

생성자의 WRITE 행은 삭제하거나 READ로 내릴 수 없다. MASTER도 생성자 권한 행을 제거하지 못한다. 생성자 계정을 비활성화할 수는 있다. 그 경우에도 권한 행은 남고, MASTER가 프로젝트 관리를 계속한다. 생성자 이전 기능은 1차에 없다.

### 4.2 프로젝트 상태

1차에서 프로젝트를 물리 삭제하지 않는다.

| 상태 | 조회 | 문서·에러 코드·일반 문서 수정 | 멤버 변경 | 제목·설명 수정 |
|---|---|---|---|---|
| ACTIVE | 가능 | WRITE와 MASTER | MASTER와 생성자 | MASTER와 생성자 |
| ARCHIVED | 가능 | 불가 | 불가 | 불가 |

보관과 복구는 MASTER와 프로젝트 생성자만 한다. 복구는 상태를 ACTIVE로 되돌린다. 보관 중에는 문서 수정이 막히므로, 다시 수정하려면 먼저 복구한다. 복구 자체는 규격 문서 version을 올리지 않는다. 프로젝트 행의 version만 올린다.

목록에는 ACTIVE와 ARCHIVED를 함께 보여 준다.

### 4.3 권한 표

| 동작 | 로그인만 | READ | WRITE | 생성자 | MASTER |
|---|---|---|---|---|---|
| 제목 목록 | 가능 | 가능 | 가능 | 가능 | 가능 |
| 상세·조회·Markdown | 불가 | 가능 | 가능 | 가능 | 가능 |
| ACTIVE 문서·에러 코드 편집 | 불가 | 불가 | 가능 | 가능 | 가능 |
| ARCHIVED 내용 수정 | 불가 | 불가 | 불가 | 불가 | 불가 |
| 보관 / 복구 | 불가 | 불가 | 불가 | 가능 | 가능 |
| 제목·설명 수정 | 불가 | 불가 | 불가 | ACTIVE에서 가능 | ACTIVE에서 가능 |
| 멤버 권한 변경 | 불가 | 불가 | 불가 | ACTIVE에서 가능 | ACTIVE에서 가능 |
| 생성자 WRITE 제거 | 불가 | 불가 | 불가 | 불가 | 불가 |

생성자는 WRITE를 가지므로 문서 편집 열의 권한도 가진다. 생성자 열은 프로젝트 관리 권한을 추가로 적는다.

## 5. 문서 종류

### 5.1 공식 규격 문서

프로젝트마다 다음 문서는 최대 1개다.

| 종류 | 코드 | 문서 안의 항목 |
|---|---|---|
| API | `API` | Endpoint |
| MQTT | `MQTT` | Topic |
| WebSocket | `WEBSOCKET` | 메시지·이벤트 |
| 장비 프로토콜 | `DEVICE_PROTOCOL` | 명령. JSON 메시지와 바이너리 레이아웃을 모두 표현 |

중복 생성은 서비스 검증과 DB UNIQUE로 막는다.

문서가 없으면 빈 문서를 자동으로 만들지 않는다. WRITE 또는 MASTER가 ACTIVE 프로젝트에서 해당 종류를 만든다. 이 상태가 "아직 생성되지 않음"이다. 행이 없다.

한 번 만든 공식 문서의 ID와 변경 이력은 유지한다. 1차에서는 공식 문서의 물리 삭제, 슬롯 비우기, 초기화, 비활성화를 제공하지 않는다. 항목이 없는 문서는 생성 직후의 빈 문서일 뿐이며, 초기화로 만든 상태와 구분하는 기능도 1차에는 없다.

항목의 추가, 수정, 삭제는 문서 삭제가 아니다. 해당 항목만 반영하고 문서 version과 이력을 남긴다.

초안, 승인, 확정 워크플로는 없다. 저장에 성공한 최신 버전이 공식 규격이다.

장비 프로토콜은 JSON 본문만 있다고 가정하지 않는다. 바이트 Offset, Length, Endian과 HEX 예시를 저장하고 조회한다.

### 5.2 일반 문서와 프로젝트 산출물

프로젝트 종료 후 SW, APP, FW, GW, HW가 남긴 기술 문서와 절차를 같은 프로젝트에서 조회하는 것이 이 기능의 목적이다.

일반 문서는 개수 제한이 없다. 예시는 다음과 같다.

- 업무 프로세스 정의
- 시스템 연동 흐름
- 장비 설치 가이드
- 개발 및 테스트 절차
- 부서별 기술 문서
- 기타 프로젝트 산출물

각 문서는 제목, 담당 부서, Markdown 본문, 작성자, 수정자, version, 변경 이력, Markdown 복사와 다운로드를 가진다. 담당 부서는 자유 입력이다. 부서 마스터 테이블은 만들지 않는다. 목록에서 빼는 삭제는 행을 물리 삭제하지 않고 숨긴다. 마지막 이력은 남긴다.

편집은 Markdown 입력과 실시간 미리보기다. 규격용 필드 편집기를 일반 문서에 쓰지 않는다.

첨부파일과 산출물 결재는 1차에서 제외한다.

## 6. 변경 이력

공식 규격 문서, 일반 문서, 에러 코드는 저장이 성공했을 때만 이력을 남긴다.

공통 항목은 수정자, 수정 시각, 변경 사유, 저장 후의 version, 그 버전의 스냅샷이다.

규격 문서의 비교 화면은 항목 추가, 삭제, 수정을 구분해서 보여 준다. 기준 키는 항목 UUID다.

에러 코드의 설명, 조건, 처리 방법을 바꾸면 에러 코드 version만 오른다. 규격 항목이 코드를 연결하거나 끊을 때만 그 공식 문서 version이 오른다. 조회 화면의 코드 설명은 에러 코드의 최신 값이다.

충돌이 나거나 검증에 실패하면 이력을 만들지 않는다.

## 7. 동시 수정 방지

공식 규격 문서는 version 하나를 가진다. 항목만 저장해도 그 version을 검사하고 1 증가시킨다.

저장 API는 변경된 항목만 받는다. 클라이언트가 문서의 전체 항목 목록을 다시 보내 통째로 교체하지 않는다.

예시:

1. A와 B가 version 5를 보고 있다.
2. A가 `/login`만 저장해 version 6이 된다.
3. B가 `/devices`를 저장하면 409다.
4. B의 입력은 화면에 남는다.
5. B가 최신 문서를 조회해 A의 `/login`과 비교한다.
6. B가 version 6을 명시해 `/devices`만 다시 저장한다.
7. 서버는 `/devices` 행만 갱신한다. `/login`은 A가 저장한 내용 그대로다.

같은 항목을 두 사람이 고친 경우에는, B가 최신본과 비교한 뒤 다시 저장하면 그 항목만 B의 내용이 된다. 다른 항목은 바뀌지 않는다. 자동 병합과 자동 덮어쓰기는 하지 않는다.

409 응답에는 최신 본문을 넣지 않는다. 클라이언트가 조회 API로 받는다.

실시간 공동 편집, 편집자 표시, 문서 잠금은 범위 밖이다.

일반 문서와 에러 코드는 행 하나가 저장 단위다. 각각 자신의 version으로 잠근다.

문서 전체를 한 번에 교체하는 API는 1차에 만들지 않는다.

## 8. Markdown 복사와 다운로드

공식 규격 문서와 일반 문서는 최신 저장본을 Markdown으로 복사하고 파일로 내려받는다. 조회 화면과 같은 데이터를 서버가 만든다.

포함되는 정보는 구조, 필드 이름, 타입, 필수 여부, 설명, 예시, 중첩 경로, 관련 에러 코드다. 장비 프로토콜은 Offset, Length, Endian, HEX 예시를 포함한다.

항목 하나의 Markdown 복사는 후순위다.

## 9. 에러 코드

프로젝트 단위로 정의한다.

- 코드
- 분류
- 설명
- 발생 조건
- 처리 방법
- 관련 규격 항목

한 코드는 API, MQTT, WebSocket, 장비 프로토콜이 함께 참조할 수 있다. 프로젝트 안에서 코드 문자열은 중복될 수 없다.

다른 항목이 참조 중이면 코드 삭제를 거절한다. 참조가 없을 때의 삭제는 행과 변경 이력을 지우지 않는다. `deleted_at`만 기록한다. 목록과 새 연결에서는 빠지고, 이력과 과거 스냅샷은 남는다. 에러 코드 기능의 구현 시점은 P1이다.

## 10. 기술과 운영 제약

- Backend: Go, Gin, GORM, MariaDB
- Frontend: React, TypeScript, Vite
- 계층: Handler, Service, Repository
- 스키마는 명시적 SQL이다. GORM AutoMigrate는 쓰지 않는다.
- 운영: Windows 서버. Go 실행파일을 Windows Service로 등록
- React 운영 파일은 `npm run build` 결과다. 운영에서 `npm run dev`를 쓰지 않는다
- Backend 포트 8090, Vite 개발 포트 487, DB 이름 `interface_hub`, Windows Service 이름 `interface_hub`
- 설정, 로그, JWT Secret, 배포 폴더는 익명 게시판과 분리한다
- 개발 PC의 포트 상태는 운영 서버 상태가 아니다. 운영 서버의 점유는 배포 직전에 확인한다
- 기존 익명 게시판은 중지하거나 수정하지 않는다
- 실제 배포와 서비스 등록은 별도 승인 후 한다

## 11. 제품 범위와 구현 단계

OQ-01부터 OQ-18의 정책은 유지한다. 이 장은 정책을 바꾸지 않고, 약 2주의 세미나 일정에서 무엇을 먼저 동작시킬지만 나눈다.

세미나에서 보여줄 시스템은 화면만 있는 Mock이 아니다. Go, MariaDB, React가 연결된 실제 저장과 조회여야 한다.

한 Task가 끝나면 개발자 확인 전에 다음 Task로 넘어가지 않는다. 진행 상태는 `docs/tasks.md`가 기준이다.

### P0 — 세미나 MVP

반드시 동작시켜야 한다.

- Go, Gin, GORM, MariaDB, React, TypeScript, Vite
- 로그인과 최소 계정 관리
- 프로젝트 생성, 목록, 상세
- 프로젝트 READ/WRITE 검증
- API 공식 규격 문서 1개와 Endpoint 등록·수정·삭제
- API 구조화 편집기, 중첩 Object/Array, Request/Response, JSON 예시
- API 조회 화면
- 문서 version, Optimistic Locking, 수정 이력, 버전 비교
- API 문서 Markdown 복사와 다운로드
- 운영용 React 빌드를 Go가 정적 파일로 제공
- 실제 DB와 브라우저 검증

P0의 규격 종류는 API뿐이다. MQTT, WebSocket, 장비 프로토콜, 일반 문서, 에러 코드 화면은 P0에서 동작하는 것처럼 두지 않는다.

### P1 — P0가 끝난 뒤 시간이 남을 때

설계와 테이블 형태는 유지하고, 구현만 뒤로 미룬다. 순서는 바꿀 수 있으며 개발자 승인이 필요하다.

1. MQTT 편집과 조회
2. WebSocket 편집과 조회
3. 일반 문서와 부서별 산출물
4. 장비 프로토콜 편집과 조회
5. 프로젝트 공통 에러 코드

### P2 — 세미나 이후

- 사용자 일괄 등록과 일괄 초기화
- 계정 관리 편의 기능
- 파일 첨부
- 실시간 공동 편집과 편집자 표시
- 고급 검색과 그 밖의 부가 기능

P1과 P2라고 적힌 요구를 문서에서 삭제하지 않는다.

P0에서 만들지 않는 것은 이전과 같다. 공식 규격 문서의 삭제와 초기화, 프로젝트 물리 삭제, 문서 전체 교체 API, 첨부파일, 결재, 초안/확정, 항목 하나의 Markdown 복사, Refresh Token, 자동 병합은 해당 단계에도 포함하지 않는다.

### P0가 만드는 저장 구조

P0 Migration은 다음 테이블만 만든다.

- `schema_migrations`
- `users`
- `password_reset_tokens`
- `projects`
- `project_members`
- `spec_documents`
- `spec_items`
- `spec_document_revisions`

`spec_documents.kind`의 허용 값에는 MQTT, WebSocket, 장비 프로토콜을 미리 넣어 둔다. P1에서 종류 제약을 바꾸지 않기 위해서다. P0 API는 `API`만 받는다.

`general_documents`, `error_codes`, `spec_item_error_codes`는 P1 Migration이다. P0 항목 저장은 `errorCodeIds`를 빈 배열만 허용한다. 값이 있으면 400을 반환하고, P1에서 연결 테이블을 켠 뒤 같은 필드를 사용한다.

### P0 화면

로그인, 최소 계정 관리, 프로젝트 목록·상세, API 편집, API 조회, 이력·비교, Markdown이다.

P1 메뉴는 활성 버튼으로 두지 않는다. 준비 중이라는 문구만 둘 수 있고, 가짜 데이터나 저장되는 것처럼 보이는 폼은 두지 않는다.

## 12. 개발 진행 방식

1. 확정된 Markdown을 기준으로 구현한다.
2. 한 번에 하나의 수직 기능만 구현한다.
3. 테스트와 결과를 보고한다.
4. 개발자가 확인하기 전에 다음 기능으로 넘어가지 않는다.
5. 실제 DB와 브라우저 검증은 해당 기능이 생겼을 때 한다.
6. 빌드와 내부 서버 배포는 별도 승인 후 한다.

## 13. 확정 정책 기록

| 번호 | 확정 내용 |
|---|---|
| OQ-01 | MASTER는 모든 프로젝트의 상세, 문서, 이력, 멤버 관리에 접근한다. 수정자는 MASTER 본인으로 기록한다 |
| OQ-02 | 권한 변경은 MASTER와 프로젝트 생성자만 한다. 생성자 WRITE는 제거할 수 없다 |
| OQ-03 | 프로젝트 물리 삭제는 없다. ACTIVE / ARCHIVED. 보관 중 내용 수정은 불가. 복구는 MASTER와 생성자 |
| OQ-04 | 공식 문서를 물리 삭제하거나 이력을 다른 테이블로 옮기지 않는다. 1차에서 삭제와 초기화는 제외한다 |
| OQ-05 | 일반 문서는 Markdown과 실시간 미리보기. 개수 제한 없음. 부서는 자유 입력 |
| OQ-06 | 첨부파일은 1차 제외 |
| OQ-07 | 30분 일회용 링크. 메일 발송은 DB 트랜잭션 밖에서 처리한다. 절차는 architecture.md |
| OQ-08 | 본인 비밀번호 변경은 1차 포함 |
| OQ-09 | MASTER 여러 명. 최초 계정은 CLI. 기동 시 자동 생성 없음 |
| OQ-10 | JWT 8시간. Refresh Token 없음 |
| OQ-11 | 목록에 제목, 상태, 생성자, 생성일, 내 권한. 설명과 본문은 권한이 있을 때만 |
| OQ-12 | 에러 코드 본문 수정은 코드 version만. 연결 변경은 규격 문서 version |
| OQ-13 | 이력 목록과 버전 비교를 1차에 포함한다. 추가·삭제·수정을 구분한다 |
| OQ-14 | Optimistic Locking. 409여도 입력을 유지한다. 자동 병합과 자동 덮어쓰기 없음 |

| OQ-17 | 계정 일괄 처리는 1차 제외 |
| OQ-18 | 초안/승인/확정 상태는 없다. 최신 저장본이 공식본 |

## 14. 구현 순서

Task 정의, 완료 조건, 체크 상태는 `docs/tasks.md`를 따른다.

P0는 골격, 로그인, 프로젝트와 권한, API 저장, API 화면, 이력과 충돌, Markdown, 통합 검증 순이다. API 저장과 조회가 브라우저에서 확인되기 전에 MQTT를 구현하지 않는다.
